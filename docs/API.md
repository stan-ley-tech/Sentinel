# Sentinel API Reference

Two APIs: the **control plane's** (Python/FastAPI, this document) and the
**gateway's own headers/behavior** (what a client sends to get through
Sentinel itself). All bodies are JSON except the OAuth token endpoint
(form-encoded, per the OAuth2 spec) and the Admin API's error format,
which is always `{"error": "<message>" }` — actually FastAPI's own
validation errors use `{"detail": ...}`; endpoints implemented in this
project use `{"error": "..."}`.

Interactive docs for the control plane are also auto-generated by FastAPI
at `/docs` when it's running.

## Authentication / trust boundaries

Three separate credentials, three separate trust boundaries:

| Token | Env var | Used for |
|---|---|---|
| Admin token | `SENTINEL_ADMIN_TOKEN` | The Admin API (`/admin/*`) — human operators, CI |
| Internal token | `SENTINEL_INTERNAL_TOKEN` | `/internal/*` — the gateway only |
| Per-key credentials | (issued via Admin API) | End callers going *through* the gateway |

The dashboard (`/dashboard`) uses HTTP Basic auth — any username, the
admin token as the password — so a browser can log in with a native
prompt instead of a custom header.

## Admin API

All `/admin/*` endpoints require `Authorization: Bearer <SENTINEL_ADMIN_TOKEN>`.

### Roles

- `POST /admin/roles` — `{"name": "reader", "permissions": ["orders:read"]}` → `201`
- `GET /admin/roles` — list all roles
- `GET /admin/roles/{name}` — `404` if not found
- `DELETE /admin/roles/{name}` — `204`; `409` if still assigned to an API key

### API keys

An API key doubles as an OAuth client (see below): its `id` is the OAuth
`client_id`, and its plaintext key is the OAuth `client_secret`.

- `POST /admin/keys` —
  ```json
  {
    "name": "Mobile App",
    "role": "reader",
    "rate_limit_per_second": 10,
    "rate_limit_burst": 20,
    "quota_limit": 100000,
    "quota_period": "day"
  }
  ```
  → `201` with the plaintext `key` and `signing_secret` — **shown exactly
  once**; only a SHA-256 hash of the key is stored server-side. `role`
  must already exist. `quota_period` is `"day"` or `"month"`, required
  when `quota_limit` is set. Rate limit / quota fields are all optional —
  omitted means "use the gateway's default" (rate limit) or "unlimited"
  (quota).
- `GET /admin/keys` / `GET /admin/keys/{id}` — never returns the
  plaintext key or signing secret again.
- `PATCH /admin/keys/{id}` — partial update (`enabled`,
  `rate_limit_per_second`, `rate_limit_burst`, `quota_limit`,
  `quota_period`).
- `DELETE /admin/keys/{id}` — `204`.

### Routes

- `POST /admin/routes` / `PUT /admin/routes/{id}` —
  ```json
  {
    "path_prefix": "/v1/orders",
    "upstreams": ["http://127.0.0.1:9001", "http://127.0.0.1:9002"],
    "strip_prefix": true,
    "auth_required": true,
    "required_permission": "orders:read",
    "require_signature": false
  }
  ```
  `path_prefix` must start with `/`; `upstreams` must be non-empty
  `http(s)://` URLs; `require_signature: true` requires `auth_required:
  true` (validated — a signature is only meaningful tied to an
  authenticated identity's signing secret). Multiple upstreams are
  round-robin load balanced across whichever are currently healthy and
  not circuit-broken.
- `GET /admin/routes` / `GET /admin/routes/{id}`
- `DELETE /admin/routes/{id}` — `204`.

### IP rules

- `POST /admin/ip-rules` — `{"cidr": "10.0.0.0/8", "action": "deny", "priority": 10}`.
  `action` is `"allow"` or `"deny"`; `cidr` validated via Python's
  `ipaddress` module. Higher `priority` is evaluated first.
- `GET /admin/ip-rules` — ordered by priority, highest first.
- `DELETE /admin/ip-rules/{id}` — `204`.

## OAuth2 (`client_credentials`)

`POST /oauth/token` — form-encoded, no auth header:

```
grant_type=client_credentials&client_id=<key id>&client_secret=<plaintext key>
```

→ `200`:
```json
{ "access_token": "<HS256 JWT>", "token_type": "bearer", "expires_in": 3600 }
```

`401 invalid_client` for a wrong secret, unknown `client_id`, or a
disabled key. `400 unsupported_grant_type` for anything but
`client_credentials`. The issued JWT's claims are `sub` (the key id) and
`role` (the key's role *at issuance time* — the gateway re-resolves the
current role from config on every request regardless, so a later role
change still takes effect immediately).

## Internal endpoints (gateway only)

All require `Authorization: Bearer <SENTINEL_INTERNAL_TOKEN>`.

- `GET /internal/config` — the full policy snapshot the gateway polls
  and hot-reloads from: `jwt_secret`, `roles` (name → permissions),
  `api_keys` (including `key_hash` and the plaintext `signing_secret`,
  but never the plaintext key itself), `routes`, `ip_rules`.
- `POST /internal/audit` — `{"entries": [...]}`, one object per request
  the gateway processed (camelCase field names — see
  `gateway/src/observability/auditLog.ts`'s `AuditEntry`). Stored,
  trimmed to the most recent 5,000 rows.
- `POST /internal/metrics` — the gateway's latest metrics snapshot
  (camelCase — see `gateway/src/observability/metrics.ts`'s
  `MetricsSnapshot`), overwriting the previously stored one.

## Dashboard

`GET /dashboard` — HTML, HTTP Basic auth (any username, admin token as
password), auto-refreshes every 5s. Shows upstream health/circuit state,
API keys, routes, IP rules, request/latency/rejection metrics, and the
most recent 50 audit log entries.

## Talking to the gateway itself

These are the headers a client sends *through* Sentinel, not to the
control plane.

| Header | Purpose |
|---|---|
| `X-Api-Key: <plaintext key>` | API key authentication |
| `Authorization: Bearer <JWT>` | OAuth-issued JWT authentication |
| `X-Signature: <hex HMAC-SHA256>` | Required on `require_signature` routes — see below |
| `X-Signature-Timestamp: <unix ms>` | Required alongside `X-Signature`; rejected outside a 5-minute window |
| `X-Nonce: <unique per request>` | Required alongside `X-Signature`; rejected if reused within that window |

**Computing a request signature:**

```
signature = hex(HMAC-SHA256(signing_secret, "<timestamp>.<nonce>." + raw_body))
```

using the API key's `signing_secret` (returned once at key creation).
See `test/integration/run_e2e.py`'s Scenario 4 for a complete worked
example in Python, or `gateway/src/crypto/hmac.ts` for the verifier.

**Gateway's own endpoints** (not proxied, handled directly):

- `GET /healthz` — `{"status": "ok"}`
- `GET /metrics` — Prometheus text exposition format: request counts by
  route+status, average latency by route, rejection counts by stage,
  and per-upstream health/circuit-breaker gauges.

**Response codes a caller may see from the gateway itself** (as opposed
to a response proxied through from an upstream): `401` (missing/invalid
credentials, or a stale/expired signature), `403` (IP denied, or RBAC
forbidden), `413` (body too large), `429` (rate limit or quota
exceeded), `503` (no healthy, non-circuit-broken upstream), `502`
(upstream connection failed). Every non-2xx response from the gateway
itself is `{"error": "<message>"}`.
